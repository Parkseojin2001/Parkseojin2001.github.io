## SQL과 데이터 프레임 API는 같은 것일까?

---

`spark.sql("...")`은 SQL 문자열을 실행하고 **데이터 프레임을 반환**한다. 그래서 SQL로 시작해서 데이터 프레임 API로 이어 가거나 그 반대로 해도 된다.

책은 미국 항공편 지연 데이터(`departuredelays.csv`)로 예제를 진행한다. 데이터 프레임을 SQL에서 쓰려면 먼저 임시 뷰로 등록한다.

```python
df = (spark.read.format("csv")
      .option("inferSchema", "true")   # 큰 파일이라면 스키마를 직접 주자 (3장 실험 참고)
      .option("header", "true")
      .load(csv_file))
df.createOrReplaceTempView("us_delay_flights_tbl")
```

아래 두 코드는 **같은 쿼리**다.

```python
# SQL
spark.sql("""SELECT distance, origin, destination
             FROM us_delay_flights_tbl WHERE distance > 1000
             ORDER BY distance DESC""").show(10)

# 데이터 프레임 API
from pyspark.sql.functions import col, desc
(df.select("distance", "origin", "destination")
   .where(col("distance") > 1000)
   .orderBy(desc("distance"))).show(10)
```

두 쿼리에 `explain()`을 붙여 보면 같은 물리 계획이 나온다. 둘 다 카탈리스트를 거치기 때문에 **성능 차이가 없고**, 팀이나 상황에 맞게 읽기 쉬운 쪽을 고르면 된다.

## 테이블을 지우면 데이터도 지워질까?

---

스파크 테이블에는 **데이터**와 **메타데이터**(스키마, 테이블 이름, 파티션, 데이터의 물리적 위치 등)가 있다. 메타데이터는 기본적으로 하이브 메타스토어(`/user/hive/warehouse`)에 저장되며, `spark.sql.warehouse.dir` 설정으로 위치를 바꿀 수 있다.

테이블은 데이터를 누가 관리하느냐에 따라 두 종류로 나뉜다.

| | 관리형 테이블 (managed) | 비관리형 테이블 (unmanaged, external) |
|---|---|---|
| 스파크가 관리하는 것 | 메타데이터 **와 데이터** | 메타데이터만 |
| 데이터 위치 | 웨어하우스 디렉터리 | 내가 지정한 경로 (S3, HDFS, 카산드라 등) |
| `DROP TABLE` 하면 | 메타데이터와 **데이터 파일까지 삭제** | 메타데이터만 삭제, 파일은 남음 |

```python
spark.sql("CREATE DATABASE learn_spark_db")
spark.sql("USE learn_spark_db")

# 관리형 테이블
spark.sql("CREATE TABLE managed_us_delay_flights_tbl "
          "(date STRING, delay INT, distance INT, origin STRING, destination STRING)")
# 데이터 프레임 API로는
flights_df.write.saveAsTable("managed_us_delay_flights_tbl")

# 비관리형 테이블: 경로를 지정한다
spark.sql("""CREATE TABLE us_delay_flights_tbl
             (date STRING, delay INT, distance INT, origin STRING, destination STRING)
             USING csv OPTIONS (PATH '/databricks-datasets/learning-spark-v2/flights/departuredelays.csv')""")
# 데이터 프레임 API로는
(flights_df.write
           .option("path", "/tmp/data/us_flights_delay")
           .saveAsTable("us_delay_flights_tbl"))
```

### 실험: 정말로 파일이 지워질까?

관리형 테이블과 비관리형 테이블을 하나씩 만들고 `DESCRIBE TABLE EXTENDED`로 종류를 확인한 뒤, 둘 다 `DROP TABLE` 해서 파일이 남는지 봤다. (PySpark 3.5.3, 로컬)

```python
spark.sql("CREATE TABLE managed_t USING parquet AS SELECT * FROM range(5)")

spark.range(5).write.parquet(ext_path)
spark.sql(f"CREATE TABLE unmanaged_t USING parquet LOCATION '{ext_path}'")

spark.sql("DESCRIBE TABLE EXTENDED managed_t").filter("col_name = 'Type'").show()
# → Type | MANAGED    (위치: <warehouse>/managed_t)
spark.sql("DESCRIBE TABLE EXTENDED unmanaged_t").filter("col_name = 'Type'").show()
# → Type | EXTERNAL   (위치: 내가 지정한 ext_path)

spark.sql("DROP TABLE managed_t")
spark.sql("DROP TABLE unmanaged_t")
```

| 테이블 | DROP 후 결과 |
|---|---|
| `managed_t` | 웨어하우스의 `managed_t` 디렉터리가 **사라졌다** |
| `unmanaged_t` | `ext_path`의 파케이 파일 4개가 **그대로 남았다** |

> 스파크 SQL의 `CREATE TABLE ... AS SELECT`는 `USING parquet` 같은 포맷을 지정하지 않으면 하이브 테이블로 만들려고 해서, 하이브 지원 없이 실행한 로컬 세션에서는 `NOT_SUPPORTED_COMMAND_WITHOUT_HIVE_SUPPORT` 에러가 났다. 로컬에서 따라 할 때는 `USING parquet`을 붙이자.
{: .prompt-tip }

원본 데이터를 다른 시스템도 함께 쓰거나 실수로 지워지면 안 되는 경우에는 **비관리형 테이블**이 안전하다.

## 테이블과 뷰는 무엇이 다를까?

---

뷰는 기존 테이블 위에 만든 **쿼리 결과의 이름**이다. 데이터를 소유하지 않기 때문에, 스파크 애플리케이션이 끝나면 테이블은 남지만 뷰는 사라진다.

| 종류 | 볼 수 있는 범위 | 접근 방법 |
|---|---|---|
| 임시 뷰 | 하나의 `SparkSession` | `뷰이름` |
| 전역 임시 뷰 | 같은 애플리케이션의 모든 `SparkSession` | `global_temp.뷰이름` |

```python
df_sfo = spark.sql("SELECT date, delay, origin, destination FROM us_delay_flights_tbl WHERE origin = 'SFO'")
df_jfk = spark.sql("SELECT date, delay, origin, destination FROM us_delay_flights_tbl WHERE origin = 'JFK'")

df_sfo.createOrReplaceGlobalTempView("us_origin_airport_SFO_global_tmp_view")
df_jfk.createOrReplaceTempView("us_origin_airport_JFK_tmp_view")

spark.read.table("global_temp.us_origin_airport_SFO_global_tmp_view")   # 전역 뷰는 global_temp 접두사
spark.read.table("us_origin_airport_JFK_tmp_view")

spark.catalog.dropGlobalTempView("us_origin_airport_SFO_global_tmp_view")
spark.catalog.dropTempView("us_origin_airport_JFK_tmp_view")
```

### 메타데이터, 캐싱, 테이블 읽기

메타데이터는 스파크 SQL의 **카탈로그**로 조회한다.

```python
spark.catalog.listDatabases()
spark.catalog.listTables()
spark.catalog.listColumns("us_delay_flights_tbl")
```

테이블과 뷰도 데이터 프레임처럼 캐시할 수 있다. 스파크 3.0부터는 `LAZY`를 붙이면 처음 쓰일 때 캐시한다.

```sql
CACHE [LAZY] TABLE <table-name>
UNCACHE TABLE <table-name>
```

테이블은 SQL이나 `spark.table()`로 데이터 프레임이 된다.

```python
us_flights_df = spark.sql("SELECT * FROM us_delay_flights_tbl")
us_flights_df2 = spark.table("us_delay_flights_tbl")
```

## 왜 파케이를 기본 포맷으로 쓸까?

---

파케이는 스파크의 **기본 데이터 소스**이며, 많은 빅데이터 도구가 지원하는 오픈소스 **컬럼 기반** 파일 포맷이다. 책은 데이터를 변환·정리한 뒤에는 파케이로 저장해 다운스트림에서 쓰라고 권한다. 파케이 파일은 데이터 파일, 메타데이터, 상태 파일이 들어 있는 디렉터리 형태로 저장되며, 푸터의 메타데이터에 스키마와 컬럼 통계가 들어 있다.

```python
# 읽기: 스키마를 줄 필요가 없다
df = spark.read.format("parquet").load(path)

# SQL로 바로 비관리형 뷰 만들기
spark.sql("""CREATE OR REPLACE TEMPORARY VIEW us_delay_flights_tbl
             USING parquet OPTIONS (path "/databricks-datasets/.../2010-summary.parquet/")""")

# 쓰기
(df.write.format("parquet")
   .mode("overwrite")
   .option("compression", "snappy")
   .save("/tmp/data/parquet/df_parquet"))

# 테이블로 쓰기
df.write.mode("overwrite").saveAsTable("us_delay_flights_tbl")
```

### 실험: CSV와 파케이, 얼마나 다를까?

3장에서 만든 100만 행 CSV(`name`, `age`, `city`)를 파케이로 저장하고, 크기와 `age` 한 컬럼의 평균을 구하는 시간을 비교했다. 시간은 첫 실행을 버리고 두 번째 실행을 쟀다.

| | CSV | 파케이 (snappy) |
|---|---|---|
| 파일 크기 | 20.7MB | **5.9MB** |
| `avg(age)` 시간 | 0.16초 | **0.04초** |

파케이에서 `age > 70` 필터를 걸고 실행 계획을 보면 이유가 드러난다.

```text
*(1) Filter (isnotnull(age) AND (age > 70))
+- *(1) ColumnarToRow
   +- FileScan parquet [age] Batched: true, ... PushedFilters: [IsNotNull(age), GreaterThan(age,70)],
                              ReadSchema: struct<age:int>
```

- **`FileScan parquet [age]`**: 컬럼 기반이라 `age` 컬럼만 디스크에서 읽는다. CSV는 한 줄을 통째로 파싱해야 한다.
- **`Batched: true`**: 컬럼 단위로 묶어 벡터화해서 읽는다. CSV 스캔은 `Batched: false`였다(3장 실험).
- **`PushedFilters`**: 파케이는 블록별 최솟값·최댓값 통계를 갖고 있어서, 조건에 맞는 값이 없는 블록은 아예 건너뛸 수 있다.
- 같은 타입 값이 한 컬럼에 모여 있으니 압축도 잘 된다. 이번 데이터에서는 약 3.5배 작아졌다.

> 시간 차이는 로컬의 작은 데이터라 절댓값보다 비율로 보는 게 맞다. 데이터가 커지고 컬럼이 많아질수록, 그리고 S3처럼 읽기 비용이 큰 저장소일수록 "필요한 컬럼만 읽는다"는 차이가 더 커진다.
{: .prompt-tip }

### 그 밖의 포맷

| 포맷 | 특징 |
|---|---|
| JSON | 읽기 쉬운 텍스트 포맷. 한 줄에 객체 하나(단일 라인 모드)가 기본이고, 여러 줄에 걸친 객체는 `multiLine` 옵션을 `true`로 |
| CSV | 스프레드시트에서 바로 만들 수 있어 분석가들이 많이 쓴다. 구분자를 바꿀 수 있다 |
| 에이브로 | 스파크 2.4부터 내장. 카프카 메시지 직렬화에 많이 쓰이고, JSON과 직접 매핑된다 |
| ORC | 파케이처럼 컬럼 기반. `spark.sql.orc.impl=native`, `spark.sql.orc.enableVectorizedReader=true`면 벡터화 리더로 행 블록 단위로 읽어 CPU 사용량을 줄인다 |
| 이미지 | 스파크 2.4부터. 딥러닝·머신러닝용 |
| 이진 파일 | 스파크 3.0부터. 파일 하나를 `path`, `modificationTime`, `length`, `content` 컬럼을 가진 행 하나로 읽는다. 다시 원래 파일로 쓰는 것은 지원하지 않는다 |

## 정리

---

- SQL과 데이터 프레임 API는 같은 엔진, 같은 실행 계획이다. 읽기 쉬운 쪽을 쓰면 된다.
- 관리형 테이블은 `DROP` 하면 **데이터 파일까지** 지워지고, 비관리형 테이블은 메타데이터만 지워진다. 원본을 지켜야 하면 비관리형으로 만들자.
- 파케이는 **필요한 컬럼만 읽고, 조건에 안 맞는 블록을 건너뛰고, 잘 압축된다.** 정리한 데이터는 파케이로 저장하자.
