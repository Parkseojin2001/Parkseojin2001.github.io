1장은 스파크의 역사와 구조를 소개하는 장이다. 역사 부분은 가볍게 넘기기 쉽지만, **"맵리듀스의 무엇이 불편했는가"**를 알면 스파크가 왜 지금과 같은 모양이 되었는지 이해된다. 이 글은 다음 세 가지 질문을 따라 정리했다.

1. 스파크 이전에는 무엇을 썼고, 무엇이 문제였을까?
2. 스파크는 그 문제를 어떤 설계로 풀었을까?
3. 스파크 애플리케이션은 클러스터 위에서 어떻게 나뉘어 돌아갈까?

## 스파크 이전: 구글의 맵리듀스와 하둡

---

### 구글은 왜 새 시스템이 필요했나

구글이 다뤄야 했던 인터넷 문서 규모는 RDBMS 같은 기존 저장 시스템으로는 색인하고 검색할 수 없었다. 그래서 구글은 세 가지 시스템을 만들었다.

| 시스템 | 역할 |
|---|---|
| GFS (구글 파일 시스템) | 여러 서버에 데이터를 나눠 저장하고, 서버 장애에도 버티는 분산 파일 시스템 |
| 빅테이블 | GFS 위에서 대규모 정형 데이터를 저장 |
| 맵리듀스(MR) | 함수형 프로그래밍(map, reduce) 개념으로 GFS·빅테이블의 데이터를 병렬 처리 |

맵리듀스의 핵심 아이디어는 **데이터를 옮기지 않고 코드를 데이터가 있는 곳으로 보내는 것**이다. 데이터 지역성과 랙 근접성을 고려해 워커 노드가 가까운 데이터를 처리하므로 네트워크 트래픽이 크게 줄어든다.

1. 워커 노드가 맵 함수로 중간 결과를 만든다.
2. 리듀스 함수가 중간 결과를 합쳐 최종 결과를 만든다.
3. 결과를 분산 저장소에 기록한다.

### 하둡 맵리듀스의 한계

구글의 GFS·맵리듀스 논문은 야후!에서 오픈소스로 구현되어 **하둡(HDFS + 맵리듀스)**이 되었고, 2006년 아파치 프로젝트가 되었다. 하둡은 널리 쓰였지만 불편한 점도 분명했다.

1. **운영이 복잡했다.** 클러스터를 관리하기 어려웠다.
2. **코드가 장황했다.** 간단한 배치 작업에도 셋업 코드가 많이 필요했고 장애 대응도 불안정했다.
3. **중간 결과를 매번 디스크에 썼다.** 맵리듀스 작업을 여러 단계로 이으면 단계마다 결과를 로컬 디스크에 쓰고 다시 읽어야 했다. 반복 계산이 많은 머신러닝에서는 치명적으로 느렸다.
4. **배치 외의 워크로드에 맞지 않았다.** 머신러닝, 스트리밍, 대화형 SQL 질의를 하려면 각각 다른 시스템(하이브, 스톰, 머하웃 등)을 따로 붙여야 했다.

이 중 3번과 4번이 스파크 설계의 출발점이다.

### 스파크의 등장

UC 버클리의 RAD 랩(이후 AMP 랩, 지금은 RISE 랩)은 2009년부터 하둡 맵리듀스를 **더 빠르고 더 쓰기 쉽게** 만드는 프로젝트를 진행했고, 이것이 스파크가 되었다.

## 스파크는 문제를 어떻게 풀었나

---

아파치 스파크는 데이터 센터나 클라우드에서 대규모 분산 데이터를 처리하기 위한 **통합 엔진**이다. 책은 설계 철학을 네 가지로 정리하는데, 각각이 위의 맵리듀스 한계와 짝을 이룬다.

| 특성 | 맵리듀스의 어떤 문제를 풀었나 | 방법 |
|---|---|---|
| 속도 | 중간 결과를 디스크에 쓰는 비용 | 중간 결과를 **메모리**에 유지하고, 전체 연산을 DAG로 계획해 최적화 |
| 사용 편리성 | 장황한 코드 | RDD 위에 데이터 프레임·데이터세트 같은 고수준 API 제공 |
| 모듈성 | 워크로드마다 다른 시스템 | SQL, 스트리밍, ML, 그래프를 **한 엔진**의 라이브러리로 제공 |
| 확장성 | 저장과 연산이 묶인 구조 | 연산에만 집중하고 저장소는 분리 (HDFS, S3, 카산드라, 몽고DB, 카프카 등) |

속도를 조금 더 풀어 보면 다음과 같다.

- **DAG 스케줄링**: 질의를 방향성 비순환 그래프(DAG)로 만들고, 태스크로 쪼개 워커 노드에서 병렬로 실행한다.
- **텅스텐 엔진**: 전체 단계 코드 생성(whole-stage code generation)으로 여러 연산을 하나의 간결한 코드로 합쳐 실행한다.
- **메모리 중심 처리**: 중간 결과를 메모리에 두고 디스크 I/O를 최소화한다.

<img src="https://www.databricks.com/sites/default/files/2023-03/largest-open-source-apache-spark.png?v=1679038543">

### 하나의 엔진, 네 개의 라이브러리

스파크는 네 개의 컴포넌트를 하나의 스택으로 제공한다. 어떤 컴포넌트를 쓰든, 어떤 언어로 쓰든 결국 스파크 코어 엔진이 DAG로 바꿔 워커 노드의 JVM에서 실행한다.

<img src="https://www.skullkim-dev.com/img/2024-03-02-spark-introduction/img.png">

| 컴포넌트 | 하는 일 |
|---|---|
| 스파크 SQL | CSV, JSON, 파케이, ORC, RDBMS 테이블 등 정형 데이터를 읽고 SQL로 질의 |
| 스파크 MLlib | 데이터 프레임 기반 머신러닝 API (특성 추출, 파이프라인, 모델 저장) |
| 정형화 스트리밍 | 스트림을 **끝없이 행이 추가되는 테이블**로 보고, 정적 테이블처럼 질의 |
| GraphX | 그래프 조작과 그래프 병렬 연산 (PageRank, 연결 요소 등) |

정형화 스트리밍의 아이디어가 특히 인상적이다. 카프카에서 들어오는 데이터든 정적 파일이든 "테이블 끝에 계속 붙는 새 행"으로 보기 때문에, 스트리밍 로직을 따로 배우지 않고 같은 SQL·데이터 프레임 코드를 쓸 수 있다. 장애 복구와 늦게 도착한 데이터 처리는 스파크 SQL 엔진이 맡는다.

## 스파크 애플리케이션은 클러스터에서 어떻게 돌아갈까?

---

스파크 애플리케이션은 **드라이버 하나**와 **여러 실행기(executor)**로 이루어지고, 그 사이를 **클러스터 매니저**가 연결한다.

<img src="../assets/img/data-engineering/spark/ch01/01.png">

| 구성 요소 | 역할 |
|---|---|
| 스파크 드라이버 | `SparkSession`을 만들고, 클러스터 매니저에 자원(CPU, 메모리)을 요청하고, 작업을 DAG로 바꿔 태스크로 나눈 뒤 실행기에 분배 |
| `SparkSession` | 스파크 2.0부터 모든 기능의 단일 진입점. 설정, 데이터 읽기, 데이터 프레임 생성, SQL 실행을 모두 여기서 한다 |
| 클러스터 매니저 | 클러스터 자원을 관리·할당. standalone, 하둡 YARN, 쿠버네티스 등 (메소스는 스파크 3.2부터 deprecated) |
| 스파크 실행기 | 워커 노드에서 태스크를 실행하고 드라이버와 통신. 대부분의 배포 모드에서 노드당 하나 |

배포 모드에 따라 드라이버·실행기·클러스터 매니저가 어디서 도는지가 달라진다. 클러스터 매니저가 추상화되어 있어서 애플리케이션 코드는 그대로 둔 채 실행 환경만 바꿀 수 있다.

<img src="../assets/img/data-engineering/spark/ch01/02.png">

### 데이터는 파티션 단위로 나뉜다

물리적인 데이터는 HDFS나 클라우드 저장소에 파티션 단위로 흩어져 저장된다. 스파크는 각 파티션을 메모리의 데이터 프레임 조각으로 보고, 실행기는 가능하면 **네트워크상 가장 가까운 파티션**을 읽도록 태스크를 배정받는다. 맵리듀스의 "코드를 데이터로 보낸다"는 아이디어가 그대로 이어진 것이다.

<img src="../assets/img/data-engineering/spark/ch01/03.png">

실행기의 CPU 코어 하나가 파티션 하나를 맡아 처리하므로, **파티션 수가 곧 병렬도**다.

<img src="../assets/img/data-engineering/spark/ch01/04.png">

### 실험: 파티션은 정말 고르게 나뉠까?

책의 예제처럼 1만 개의 정수를 8개 파티션으로 만들고, 각 행이 어느 파티션에 들어갔는지 `spark_partition_id()`로 세어 봤다. (PySpark 3.5.3, `local[4]`)

```python
from pyspark.sql import functions as F

df = spark.range(0, 10000, 1, 8)          # 8개 파티션으로 생성
print(df.rdd.getNumPartitions())          # 8

(df.groupBy(F.spark_partition_id().alias("pid"))
   .count().orderBy("pid").show())
```

```text
+---+-----+
|pid|count|
+---+-----+
|  0| 1250|
|  1| 1250|
...
|  7| 1250|
+---+-----+
```

8개 파티션에 정확히 1,250개씩 들어갔다. 파티션 수를 지정하지 않고 `spark.range(0, 10000)`만 쓰면 파티션은 **4개**였다. 로컬 모드에서는 기본 병렬도가 `local[4]`의 코어 수를 따르기 때문이다.

> 파일에서 읽은 데이터는 이렇게 고르게 나뉜다는 보장이 없다. 특정 키에 데이터가 몰리면(데이터 스큐) 한 태스크만 오래 걸려 전체 작업이 늦어진다. 이후 장에서 `repartition()`과 셔플을 다룰 때 다시 나오는 문제다.

## 정리

---

- 스파크는 하둡 맵리듀스의 **디스크 기반 중간 결과**와 **워크로드별로 쪼개진 시스템** 문제를 풀려고 등장했다.
- 메모리 중심 처리와 DAG 최적화로 빠르고, SQL·스트리밍·ML·그래프를 **한 엔진**에서 처리한다.
- 애플리케이션은 드라이버가 작업을 나누고 실행기가 **파티션 단위**로 병렬 처리하는 구조이며, 파티션 수가 곧 병렬도다.
