2장은 설치 방법을 다루는 장처럼 보이지만, 핵심은 뒤쪽에 있다. **내가 쓴 코드 한 줄이 스파크 안에서 어떤 단위로 쪼개져 실행되는가**이다. 이 흐름을 알아야 이후 장의 성능 이야기(셔플, 파티션, 캐시)가 읽힌다.

이 글에서는 설치는 짧게 정리하고, 다음 세 가지 질문에 답하는 데 집중한다. 마지막 두 질문은 PySpark로 직접 실험해서 확인했다.

1. 스파크 애플리케이션은 어떤 단위로 나뉘어 실행될까? (잡 → 스테이지 → 태스크)
2. 트랜스포메이션을 쓰면 정말 아무 일도 일어나지 않을까? (지연 평가)
3. 좁은 트랜스포메이션과 넓은 트랜스포메이션은 실행 계획에서 어떻게 다를까?

## 코드는 어떤 단위로 실행될까?

---

스파크 용어는 서로 포함 관계에 있어서, 큰 단위부터 보면 이해가 쉽다.

```mermaid
flowchart LR
  A[애플리케이션<br/>드라이버 + 실행기] --> B[잡<br/>액션 1번마다 생성]
  B --> C[스테이지<br/>셔플 경계로 나뉨]
  C --> D[태스크<br/>파티션 1개 = 태스크 1개]
```

| 단위 | 언제 생기나 | 한 줄 정리 |
|---|---|---|
| 애플리케이션 | 프로그램 실행 | 드라이버 프로그램과 클러스터의 실행기(executor)로 구성 |
| `SparkSession` | 드라이버가 생성 | 스파크 기능을 쓰는 진입점. 셸에서는 `spark`로 미리 만들어져 있음 |
| 잡(job) | `count()`, `collect()`, `save()` 같은 **액션** 호출 | 액션 하나에 대응하는 병렬 연산 |
| 스테이지(stage) | 잡을 DAG로 바꿀 때 | 데이터 교환(셔플) 없이 이어서 실행할 수 있는 연산 묶음 |
| 태스크(task) | 스테이지를 실행할 때 | 실행기의 CPU 코어 하나가 파티션 하나를 처리하는 최소 단위 |

<img src="../assets/img/data-engineering/spark/ch02/04.png">

드라이버는 애플리케이션을 잡으로 바꾸고, 각 잡을 DAG(실행 계획)로 변환한다. DAG의 각 노드가 스테이지다.

<img src="../assets/img/data-engineering/spark/ch02/05.png">

모든 연산을 하나의 스테이지에서 끝낼 수는 없다. 다른 파티션의 데이터가 필요해지는 지점에서 스테이지가 나뉜다. 이 경계가 아래에서 볼 "넓은 트랜스포메이션"이다.

<img src="../assets/img/data-engineering/spark/ch02/06.png">

각 스테이지는 파티션 수만큼의 태스크로 실행된다. 코어가 16개인 실행기라면 태스크 16개를 동시에 처리할 수 있으므로, 파티션도 최소 16개는 되어야 코어를 놀리지 않는다.

<img src="../assets/img/data-engineering/spark/ch02/07.png">

## 트랜스포메이션을 쓰면 정말 아무 일도 안 일어날까?

---

스파크 연산은 두 종류로 나뉜다.

- **트랜스포메이션**: `select()`, `filter()`, `groupBy()`처럼 데이터 프레임을 새 데이터 프레임으로 바꾸는 연산이다. 원본은 바뀌지 않고(불변성), 실행되지 않은 채 **리니지(lineage)**로 기록만 된다.
- **액션**: `count()`, `collect()`, `show()`처럼 결과가 필요한 연산이다. 이때 기록해 둔 트랜스포메이션이 한꺼번에 실행된다.

<img src="../assets/img/data-engineering/spark/ch02/08.png">

이렇게 실행을 미루는 것을 **지연 평가(lazy evaluation)**라고 한다. 스파크는 액션 전까지 전체 연산을 보고 순서를 바꾸거나 합쳐서 최적화할 수 있다. 또 리니지만 있으면 결과를 다시 계산할 수 있으므로, 파티션이 유실돼도 따로 백업 없이 복구할 수 있다.

### 실험: 2천만 행에 필터를 걸면 몇 초 걸릴까?

책의 설명이 실제로도 그런지 시간과 잡 수를 재 봤다. (PySpark 3.5.3, `local[4]`)

```python
from pyspark.sql import SparkSession, functions as F

spark = SparkSession.builder.master("local[4]").getOrCreate()
st = spark.sparkContext.statusTracker()

df = spark.range(0, 20_000_000)
narrow = df.filter(F.col("id") % 2 == 0).withColumn("bucket", F.col("id") % 10)
# → 트랜스포메이션 정의: 0.0954s, 지금까지 잡 수: 0

narrow.count()
# → 액션 count(): 0.92s, 지금까지 잡 수: 2
```

- 2천만 행에 `filter`와 `withColumn`을 걸었는데 0.1초도 안 걸렸고, **잡이 하나도 생기지 않았다.** 실행 계획만 기록된 것이다.
- `count()`를 호출한 순간에야 실제 계산이 일어나 잡이 생겼다.

> 처음에 헷갈리기 쉬운 점: 액션 하나에 잡이 정확히 하나만 생기지는 않는다. 위 실험에서도 `count()` 한 번에 잡이 2개 생겼다. `count()`는 파티션별 개수를 센 뒤 셔플로 모아 합치는 집계로 처리되는데, 스파크 3.x에 기본으로 켜진 AQE가 셔플 앞부분과 뒷부분을 별도의 잡으로 실행하기 때문이다. "액션이 잡을 만든다"는 맞지만 "액션 1개 = 잡 1개"로 외우면 스파크 UI를 볼 때 혼란스럽다.

## 좁은 트랜스포메이션과 넓은 트랜스포메이션

---

트랜스포메이션은 데이터가 파티션 사이를 오가는지에 따라 둘로 나뉜다.

- **좁은 의존성**: 입력 파티션 하나로 결과 파티션 하나를 만든다. 데이터 교환이 없다. (`filter()`, `select()`, `withColumn()`)
- **넓은 의존성**: 다른 파티션의 데이터를 모아야 한다. 이 데이터 교환을 **셔플**이라 하며, 네트워크와 디스크를 쓰기 때문에 비싸다. (`groupBy()`, `orderBy()`, `join()`)

<img src="../assets/img/data-engineering/spark/ch02/10.png">

### 실험: 실행 계획에서 셔플 찾기

위의 `narrow`에 `groupBy`를 하나 붙여서 `explain()`으로 두 실행 계획을 비교했다.

```python
narrow.explain()
```

```text
*(1) Project [id#0L, (id#0L % 10) AS bucket#4L]
+- *(1) Filter ((id#0L % 2) = 0)
   +- *(1) Range (0, 20000000, step=1, splits=4)
```

```python
wide = narrow.groupBy("bucket").count()
wide.explain()
```

```text
AdaptiveSparkPlan isFinalPlan=false
+- HashAggregate(keys=[bucket#4L], functions=[count(1)])
   +- Exchange hashpartitioning(bucket#4L, 200), ENSURE_REQUIREMENTS
      +- HashAggregate(keys=[bucket#4L], functions=[partial_count(1)])
         +- Project [(id#0L % 10) AS bucket#4L]
            +- Filter ((id#0L % 2) = 0)
               +- Range (0, 20000000, step=1, splits=4)
```

비교해 보면 세 가지가 보인다.

1. **`Exchange`가 셔플이다.** 좁은 계획에는 없고 넓은 계획에만 있다. 실행 계획에서 `Exchange`를 찾으면 스테이지가 어디서 끊기는지 알 수 있다.
2. **좁은 연산들은 하나로 묶인다.** `*(1)`은 `Range → Filter → Project`가 같은 코드로 합쳐져(whole-stage codegen) 한 스테이지에서 실행된다는 뜻이다.
3. **집계는 셔플 앞뒤로 두 번 일어난다.** 셔플 전에 파티션마다 `partial_count`로 미리 세고, 셔플 뒤에 합친다. 옮길 데이터를 줄이려는 최적화다.

실제 실행에서도 차이가 났다. 같은 데이터에서 `narrow.limit(5).collect()`는 스테이지 1개로 끝났지만, `wide.collect()`는 셔플 경계를 기준으로 스테이지가 나뉘어 총 3개가 실행됐다. (스파크 3.x는 기본으로 AQE가 켜져 있어서, 셔플 앞부분을 먼저 실행한 뒤 결과 크기를 보고 뒷부분 계획을 다시 세운다. 그래서 잡도 2개로 나뉘어 보인다.)

## 스파크 UI에서 확인하기

---

드라이버는 기본으로 `http://localhost:4040`에 웹 UI를 띄운다. 위 실험을 셸에서 돌린 뒤 열어 보면, 지금까지 본 잡·스테이지·태스크를 그대로 확인할 수 있다.

- **Jobs / Stages 탭**: 잡과 스테이지 목록, 스테이지별 태스크 수와 실행 시간
- **SQL 탭**: `explain()`으로 본 실행 계획을 그림으로 표시
- **Storage / Environment / Executors 탭**: 캐시된 데이터 크기, 설정값, 실행기 상태

## 정리

---

- 스파크 코드는 **액션**을 만나야 실행되고, 실행은 **잡 → 스테이지 → 태스크** 단위로 쪼개진다.
- 스테이지는 **셔플(`Exchange`)** 지점에서 나뉜다. 넓은 트랜스포메이션이 늘수록 스테이지와 셔플 비용도 늘어난다.
- 성능을 볼 때는 `explain()`에서 `Exchange`를 먼저 찾고, 스파크 UI에서 스테이지별 시간을 확인하면 된다.
