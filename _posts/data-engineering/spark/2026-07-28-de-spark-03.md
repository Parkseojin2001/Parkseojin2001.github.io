## RDD의 무엇이 문제였을까?

---

RDD는 스파크의 가장 기본적인 추상화이며 세 가지 특성을 가진다.

| 특성 | 의미 |
|---|---|
| 의존성 | 이 RDD가 어떤 입력에서 어떻게 만들어졌는지. 결과가 유실되면 이 정보로 다시 계산한다 |
| 파티션 (지역성 정보 포함) | 작업을 나눠 실행기에서 병렬로 처리하게 해 준다. HDFS라면 데이터와 가까운 실행기에 우선 배정한다 |
| 연산 함수 | 파티션 → `Iterator[T]`. RDD에 담길 데이터를 만든다 |

문제는 연산 함수가 스파크에게 **블랙박스**라는 점이다.

- 조인이든 필터든 집계든, 스파크 눈에는 그냥 람다 함수로만 보인다.
- 파이썬 RDD에서 `Iterator[T]`의 `T`는 그냥 파이썬 객체라서 스파크가 타입을 모른다.
- 무엇을 하는지 모르니 **최적화할 수 없고**, 타입을 모르니 **압축 같은 저장 최적화도 적용할 수 없다.**

## 스파크 2.x의 해법: 구조를 부여하기

---

스파크 2.x는 연산과 데이터에 구조를 부여했다.

- 연산을 람다가 아니라 **필터, 선택, 집계, 그룹화** 같은 고수준 연산(DSL)으로 표현한다. 이제 스파크는 "무엇을 원하는지" 안다.
- 데이터를 SQL 테이블처럼 **이름과 타입이 있는 컬럼**으로 구성한다.

그 결과 코드가 표현력 있고, 단순하고, 조합하기 쉬우며, 언어가 달라도 같은 형태가 된다. 아래 코드는 이름별 평균 나이를 구하는데, **어떻게** 계산할지는 전혀 적지 않고 **무엇을** 원하는지만 적는다.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import avg

spark = SparkSession.builder.appName("AuthorsAges").getOrCreate()
data_df = spark.createDataFrame(
    [("Brooke", 20), ("Denny", 31), ("Jules", 30), ("TD", 35), ("Brooke", 25)],
    ["name", "age"])
data_df.groupBy("name").agg(avg("age")).show()
```

같은 일을 RDD로 하려면 `(name, (age, 1))` 튜플을 만들고 `reduceByKey`로 합계와 개수를 더한 뒤 다시 나누는 코드를 직접 짜야 한다. 그리고 스파크는 그 코드가 평균을 구한다는 사실을 끝내 모른다.

### 스키마는 왜 미리 정해 주는 게 좋을까?

스키마는 컬럼 이름과 타입의 정의다. 파일을 읽을 때 스키마를 미리 주면 세 가지가 좋아진다고 책은 설명한다.

1. 스파크가 타입을 추측할 필요가 없다.
2. 스키마를 알아내려고 **파일을 읽는 별도의 잡**을 만들지 않는다. 파일이 크면 이 비용이 크다.
3. 데이터가 스키마와 맞지 않으면 일찍 발견할 수 있다.

정의 방법은 두 가지이며, DDL 문자열 쪽이 짧고 읽기 쉽다.

```python
# 프로그래밍 방식
from pyspark.sql.types import *
schema = StructType([StructField("author", StringType(), False),
                     StructField("title", StringType(), False),
                     StructField("pages", IntegerType(), False)])

# DDL 방식
schema = "author STRING, title STRING, pages INT"
```

#### 실험: 스키마 추론은 정말 잡을 만들까?

2번 주장을 확인하려고 100만 행짜리 CSV(약 20MB)를 두 방식으로 읽고, **읽기만 했을 때**(액션 없이) 생긴 잡 수를 셌다. (PySpark 3.5.3, `local[4]`)

```python
st = spark.sparkContext.statusTracker()

def count_jobs(fn):
    before = set(st.getJobIdsForGroup())
    fn()
    return len(set(st.getJobIdsForGroup()) - before)

count_jobs(lambda: spark.read.option("header", True)
                              .option("inferSchema", True).csv(path))
# → 2

count_jobs(lambda: spark.read.option("header", True)
                              .schema("name STRING, age INT, city STRING").csv(path))
# → 0
```

- `inferSchema`를 켜면 **액션을 호출하지 않았는데도 잡이 2개** 생겼다. 헤더를 읽는 잡과 타입을 추론하려고 데이터를 훑는 잡이다.
- 스키마를 직접 주면 잡이 **0개**였다. 2장에서 본 지연 평가 그대로, 읽기 자체는 계획만 세운다.

> `inferSchema`는 "트랜스포메이션은 실행되지 않는다"는 규칙의 예외처럼 보인다. 데이터 프레임을 만들려면 스키마가 반드시 있어야 하므로, 스키마를 모르면 스파크가 먼저 데이터를 읽을 수밖에 없다. 실무에서 큰 파일을 읽을 때 스키마를 지정하라는 이유가 여기 있다.

### 컬럼과 로우

fire_schema = StructType([StructField('CallNumber', IntegerType(), True),

fire_df = spark.read.csv(sf_fire_file, header=True, schema=fire_schema)

fire_df.write.format("parquet").save(parquet_path)          # 파일로 저장

### 프로젝션과 필터

- **프로젝션**: 원하는 컬럼만 고른다. `select()`
- **필터**: 조건에 맞는 행만 고른다. `filter()` 또는 `where()`

```python
from pyspark.sql.functions import *

(fire_df.select("IncidentNumber", "AvailableDtTm", "CallType")
        .where(col("CallType") != "Medical Incident")
        .show(5, truncate=False))

# 호출 유형이 몇 종류인지
(fire_df.select("CallType")
        .where(col("CallType").isNotNull())
        .agg(countDistinct("CallType").alias("DistinctCallTypes"))
        .show())
```

### 컬럼 이름 바꾸기, 타입 바꾸기

데이터 프레임은 불변이므로, 아래 연산은 모두 **새 데이터 프레임**을 반환하고 원본은 그대로 남는다.

```python
new_fire_df = fire_df.withColumnRenamed("Delay", "ResponseDelayedinMins")

# 문자열 날짜를 타임스탬프로 바꾸고 원래 컬럼은 버린다
fire_ts_df = (new_fire_df
    .withColumn("IncidentDate", to_timestamp(col("CallDate"), "MM/dd/yyyy"))
    .drop("CallDate")
    .withColumn("OnWatchDate", to_timestamp(col("WatchDate"), "MM/dd/yyyy"))
    .drop("WatchDate")
    .withColumn("AvailableDtTS", to_timestamp(col("AvailableDtTm"), "MM/dd/yyyy hh:mm:ss a"))
    .drop("AvailableDtTm"))

# 타임스탬프가 되면 year() 같은 날짜 함수를 쓸 수 있다
fire_ts_df.select(year("IncidentDate")).distinct().orderBy(year("IncidentDate")).show()
```

## 데이터 프레임, 데이터세트, RDD 중 무엇을 쓸까?

---

**데이터세트**는 정적 타입(typed) API와 동적 타입(untyped) API를 모두 가진다. 스칼라에서 데이터 프레임은 사실 `Dataset[Row]`의 별칭이고, 데이터세트는 `Dataset[DeviceIoTData]`처럼 **특정 클래스로 타입이 정해진** JVM 객체의 모음이다.

<img src="../assets/img/data-engineering/spark/ch03/05.png">

파이썬과 R은 컴파일 시점에 타입을 검사하지 않는 언어라서 **데이터 프레임만** 쓸 수 있다. 데이터세트는 자바와 스칼라 전용이다.

<img src="../assets/img/data-engineering/spark/ch03/06.png">

스칼라에서는 케이스 클래스로 스키마를 정하고 `as[T]`로 데이터세트를 만든다.

<img src="../assets/img/data-engineering/spark/ch03/07.png">

```scala
case class DeviceIoTData (battery_level: Long, c02_level: Long, cca2: String, cca3: String,
  cn: String, device_id: Long, device_name: String, humidity: Long, ip: String, latitude: Double,
  lcd: String, longitude: Double, scale: String, temp: Long, timestamp: Long)

val ds = spark.read.json("/databricks-datasets/learning-spark-v2/iot-devices/iot_devices.json")
              .as[DeviceIoTData]

// 람다의 인자 d가 DeviceIoTData 객체라서, 필드 이름 오타는 컴파일 단계에서 잡힌다
val filterTempDS = ds.filter(d => d.temp > 30 && d.humidity > 70)
```

<img src="../assets/img/data-engineering/spark/ch03/08.png">

선택 기준은 길게 나열할 수 있지만, 정리하면 다음 표로 충분하다.

| 상황 | 선택 |
|---|---|
| 파이썬이나 R을 쓴다 | 데이터 프레임 |
| SQL 같은 관계형 연산, 공간·속도 효율, 컴포넌트 간 일관된 API가 필요하다 | 데이터 프레임 |
| 스칼라/자바에서 **컴파일 시점 타입 검사**가 필요하고 케이스 클래스를 만드는 게 부담스럽지 않다 | 데이터세트 |
| RDD 기반 서드파티 라이브러리를 써야 하거나, 스파크가 **어떻게** 실행할지 직접 지정해야 한다 | RDD |

RDD가 필요하면 `df.rdd`로 바꿀 수 있지만 변환 비용이 있고, 그 순간부터 아래에서 볼 최적화를 포기하게 된다.

## 스파크 SQL 엔진과 카탈리스트 옵티마이저

---

데이터 프레임, 데이터세트, SQL은 모두 같은 **스파크 SQL 엔진** 위에서 돌아간다. 이 엔진은 SQL 질의 실행, 하이브 메타스토어 접근, 여러 파일 포맷 읽기·쓰기, JDBC/ODBC 연결, 그리고 최적화된 실행 계획과 JVM 코드 생성을 맡는다.

<img src="../assets/img/data-engineering/spark/ch03/09.png">

엔진의 핵심은 **카탈리스트 옵티마이저**와 **텅스텐**이다. 카탈리스트는 쿼리를 네 단계로 바꾼다.

| 단계 | 하는 일 |
|---|---|
| 1. 분석 | 쿼리를 추상 구문 트리로 만들고, 카탈로그에서 컬럼·테이블 이름과 타입을 확인한다 |
| 2. 논리적 최적화 | 규칙 기반 최적화(필터를 앞으로 당기기, 필요 없는 컬럼 빼기, 식 단순화)와 비용 기반 최적화(CBO)를 적용한다 |
| 3. 물리 계획 | 논리 계획에 맞는 실제 연산자(어떤 조인 알고리즘을 쓸지 등)를 고른다 |
| 4. 코드 생성 | 텅스텐이 각 머신에서 실행할 자바 바이트코드를 만든다 |

<img src="../assets/img/data-engineering/spark/ch03/10.png">

<img src="../assets/img/data-engineering/spark/ch03/11.png">

### 실험: 일부러 비효율적으로 쓴 쿼리는 어떻게 바뀔까?

카탈리스트가 정말 쿼리를 고치는지 보려고, 일부러 낭비가 많은 쿼리를 짜서 `explain(True)`로 네 단계를 모두 출력했다.

```python
q = (people                                   # name, age, city 컬럼의 CSV
     .select("name", "age", "city")           # 쓸데없이 컬럼을 다시 고르고
     .withColumn("age2", F.col("age") + 1)    # 필터보다 먼저 계산하고
     .filter(F.col("age") > 30)               # 필터는 뒤에 두고
     .select("name", "age2"))                 # city는 결국 안 쓴다
q.explain(True)
```

내가 쓴 그대로의 **분석된 논리 계획**은 다음과 같다.

```text
Project [name, age2]
+- Filter (age > 30)
   +- Project [name, age, city, (age + 1) AS age2]
      +- Project [name, age, city]
         +- Relation [name,age,city] csv
```

**최적화된 논리 계획**과 **물리 계획**은 이렇게 바뀌었다.

```text
== Optimized Logical Plan ==
Project [name, (age + 1) AS age2]
+- Filter (isnotnull(age) AND (age > 30))
   +- Relation [name,age,city] csv

== Physical Plan ==
*(1) Project [name, (age + 1) AS age2]
+- *(1) Filter (isnotnull(age) AND (age > 30))
   +- FileScan csv [name,age] ... PushedFilters: [IsNotNull(age), GreaterThan(age,30)],
                                   ReadSchema: struct<name:string,age:int>
```

비교해 보면 카탈리스트가 한 일이 보인다.

1. **불필요한 `Project` 세 개가 하나로 합쳐졌다.** 내가 쓴 단계 수와 상관없이 필요한 것만 남는다.
2. **필터가 계산보다 앞으로 왔다.** `age2`는 필터를 통과한 행에서만 계산된다.
3. **`city` 컬럼은 아예 읽지 않는다.** `ReadSchema`에 `name`, `age`만 있다(컬럼 가지치기).
4. **필터가 파일 스캔까지 내려갔다.** `PushedFilters`에 조건이 들어가 있다(조건절 푸시다운). 파케이처럼 통계가 있는 포맷이라면 조건에 안 맞는 블록을 건너뛸 수 있다.
5. **`isnotnull(age)`가 자동으로 추가됐다.** `age > 30`은 null이면 어차피 거짓이라 의미는 같지만, 스캔 단계에서 null을 미리 걸러낼 수 있다.

같은 필터를 RDD 람다로 쓰면(`people.rdd.filter(lambda r: r.age > 30)`) 계보에는 `PythonRDD`와 `MapPartitionsRDD`만 보인다. 스파크는 람다 안에서 무슨 일이 일어나는지 모르므로 위의 최적화를 하나도 할 수 없다. 이 장 첫머리의 "블랙박스"가 바로 이것이다.

## 정리

---

- RDD의 연산은 스파크에게 블랙박스라서 최적화할 수 없었다. 데이터 프레임은 연산과 데이터에 **구조**를 줘서 이 문제를 풀었다.
- 큰 파일은 **스키마를 직접 지정**하자. `inferSchema`는 액션 없이도 데이터를 읽는 잡을 만든다.
- 카탈리스트는 쿼리를 **합치고, 순서를 바꾸고, 안 쓰는 컬럼과 행을 스캔 단계에서 버린다.** 내가 쿼리를 대충 써도 어느 정도 고쳐 주지만, 람다나 RDD로 넘어가는 순간 이 도움은 사라진다.
